# 이메일 정합성 관리

2026-09-15 구현·운영 반영 완료.

## 사용 방법

1. `/marketing`에서 필요하면 필터를 적용하거나 행을 선택하고 **이메일 정합성 검사**를 누른다.
2. **전체 Master / 현재 필터 결과 전체 / 직접 선택** 중 범위를 고른다. 화면에 보이는 25건과 필터 결과 전체를 구분한다.
3. `/marketing/email-checks`에서 실행 이력을, 상세 화면에서 진행률·판정·근거를 확인한다. 판정·회사·성명·이메일·DB ID로 결과를 필터링하고 전체 결과를 Excel로 다운로드한다.
4. 결과의 **회사 홈페이지·도메인 기준**, 또는 Master의 **회사·기관 → 홈페이지·이메일**에서 회사가 실제 사용하는 주소와 확인 근거를 등록한다. 기존 업무 회사명·분류와 별도 버전으로 관리한다.
5. 기준 등록·변경 후 **최신 기준으로 다시 검사**한다. 이메일 수정이 필요하면 **변경 정보 제출**로 최신 Master 값을 불러와 제출하고 기존 담당자 승인 절차를 거친다.

검사나 회사 이메일 기준 등록은 Contact의 이메일·회사명 등 기존 Master 값을 자동 변경하지 않는다. AI·Stibee·외부 이메일 검증 서비스 연결 없이 동작한다.

## 확인하는 항목과 의미

| 항목 | 판정 근거 | 판정 한계 |
|---|---|---|
| 이메일 형식 | 일반 이메일 형식, IDNA 도메인, 공개 등록 도메인 | 국제화·인용 사용자 부분은 확인 필요로 처리 |
| 회사 연관성 | 담당자가 확인한 이메일 도메인과 정확히 일치 | 공용 메일은 회사 소속을 추론하지 않음. MX 제공업체를 소속 회사로 보지 않음 |
| 메일 수신 도메인 | DNS MX와 공개 서버 주소, Null MX, A/AAAA 대체 경로 | MX 존재만으로 개인 메일함 또는 수신 성공을 보장하지 않음 |
| 회사 홈페이지 | 등록 홈페이지 또는 이메일 도메인 후보의 HTTP 응답, 최종 URL·제목, 회사명 문자열 | 응답·회사명 등장만으로 공식성이나 법인 실존을 확정하지 않음 |
| 개별 메일함 실제 존재 | 항상 미확인으로 명시 | 발송 이력·담당자 확인 또는 별도 검증 체계가 필요 |

- **근거 확인**: 형식·승인 회사 이메일 도메인·MX·등록 홈페이지 응답이 확인됨. 메일함 존재와는 별개다.
- **문제 발견**: 형식 오류, DNS 도메인 없음, 명시적인 메일 수신 거부(Null MX), 공개 수신 경로 없음.
- **확인 필요**: 회사 기준 미등록/불일치, 공용 메일, 홈페이지 후보, A/AAAA 대체 경로, DNS 일시 실패, 접속 차단·장애·인증서 오류, 다른 등록 도메인으로 이동, 판매·주차 페이지.
- **실행 오류**: 시스템이 결과 저장까지 완료하지 못한 경우. 같은 실행에서 오류·미처리를 재시도할 수 있다.

홈페이지를 등록해도 메일 도메인을 자동 승인하지 않는다. 홈페이지와 이메일 도메인이 다르면 각각 등록할 수 있다. 하위 메일 도메인도 개별 등록한다. Gmail·네이버·다음 등 대표 공용 메일은 회사 전용 도메인으로 등록할 수 없다.

## 실행·이력·권한

- 실행 생성 때 대상 Contact·회사·이메일 기준을 하나의 DB 스냅샷으로 고정한다. 일부를 검사한 후 다시 검사해도 선택한 ID 범위를 보존한다.
- 동일 실행에서는 같은 도메인·홈페이지의 조회 결과를 공유한다. 새 실행은 새로운 외부 조회를 수행한다.
- 20개 Contact를 임대하고 네트워크 작업은 5개씩 처리한다. 임대 120초, 임대 토큰이 달라지거나 만료되면 이전 작업자의 결과 저장을 거부한다.
- 요청 후 작업자를 시작하며 Vercel Cron이 5분마다 대기·만료 작업을 회수한다. 브라우저를 닫아도 이어진다. 실행 중인 작업은 최대 3개다.
- 취소 후 이미 처리된 결과를 유지한다. 같은 실행의 재시도는 미처리·실행 오류만 처리하며 이전 오류 결과는 보존한다. 네트워크의 확인 필요는 새 실행으로 다시 조회한다.
- 현재 Contact·회사·이메일 기준의 버전이 바뀌거나 검사 후 30일이 지나면 재검사를 표시한다. 지난 결과와 당시 기준은 보존한다.
- 홈페이지·도메인 기준은 변경 근거, 담당자, 이전/새 버전을 DB에 기록한다. 동시 편집 충돌은 거부한다.
- 강승억·김하연의 기존 페이지·API·RLS 제한을 적용한다. 일반 클라이언트가 네트워크 결과를 직접 쓰거나 작업자 RPC를 호출할 수 없다. Cron은 기존 `CRON_SECRET`, 작업자는 기존 서비스 역할 키로 인증한다.
- 회사 홈페이지와 도메인만 외부 조회한다. Contact 성명·이메일 사용자 부분·전화번호를 검증업체에 전송하지 않으며, 테스트 메일·SMTP 수신자 탐색을 하지 않는다.
- 홈페이지 조회는 HTTP(S), 기본 포트만 허용한다. 인증정보·검색 매개변수·IP URL·특수 도메인은 제외한다. DNS의 비공개 주소를 차단하고 검증한 공개 IP를 연결에 고정한다. 모든 리디렉션을 다시 검사한다. 시간·응답 크기·이동 횟수를 제한하며 쿠키·브라우저 인증정보를 전달하지 않는다.

## Master 레코드의 이메일 검증 이력

Master DB에서 **DB ID 클릭 → 이메일 검증 이력 → 검증 내용·판정 근거 보기**로 확인한다. 최신 검사 요약을 먼저 표시하고 이전 검사도 펼쳐 볼 수 있다. 페이지당 20건이며, 새로고침으로 진행 중인 검사의 완료 결과를 갱신한다.

- 각 이력에는 원래 검사 저장 시각, 실행 요청자, 검사 당시 이메일·회사·DB ID, 종합 판정과 주소 형식·회사 이메일 연관성·메일 수신 도메인·홈페이지·개별 메일함 판정 근거를 표시한다.
- MX 레코드, 홈페이지 URL·최종 응답·페이지 제목·확인 시각, 당시 Contact·회사·이메일 기준 버전, 검사 엔진과 원본 결과도 보존한다. 전체 검사 실행 화면으로 이동할 수 있다.
- 결과가 DB에 확정될 때 `marketing_email_results`의 트리거가 `marketing_review_events`에 같은 트랜잭션으로 이력을 추가한다. 이력 기록 실패 시 결과 및 대상 처리 완료도 롤백한다. 한 검사 시도당 `email_result_id`가 유일하므로 중복 기록하지 않는다.
- 재검사·실행 오류 재시도는 별도 이력을 추가한다. 이메일이나 회사 기준이 변경되어도 당시 정보를 덮어쓰지 않는다. 현재 버전과 다르거나 30일이 경과한 결과는 재검사 필요로 표시한다.
- 이미 수행한 검사도 결과 원본의 저장 시각·요청자·스냅샷을 그대로 옮긴다. 보완 SQL을 다시 적용해도 이력이 중복되지 않는다.
- 통합 **변경 이력** 탭에도 읽기 쉬운 이메일 검증 내용이 표시된다. 이메일 검증은 해당 Contact에만 연결하며 회사 공통 이력으로 배포하지 않는다.
- Contact 상세의 일반 변경 이력은 해당 Contact의 변경과 회사 공통 변경만 표시한다. 같은 회사의 다른 Contact 변경은 포함하지 않는다.
- 이메일 이력 조회는 기존 페이지 권한과 RLS를 적용한다. API: `GET /api/marketing/email-checks/contacts/{contactId}?page=1` → `marketing_email_contact_history` RPC. 사용자가 검사 결과나 이력을 직접 수정할 수 없다.
- 보완 마이그레이션: `docs/sql/2026-09-15-marketing-email-contact-history.sql` (이메일 정합성 SQL 이후 적용). Master 필드·버전·최종확인일은 이력 추가만으로 변경하지 않는다. 이메일 검사 시각은 별도로 기록한다.
