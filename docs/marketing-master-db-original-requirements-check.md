# 최초 요구사항 대비 최종 재점검

> 후속 처리: 아래에서 발견한 두 비-AI 항목을 수정하고 운영 반영·검증을 완료했다. 누락·형식 오류는 확인 필요로 접수하며 김하연 검수자 지정을 적용했다. 이 본문은 보완 전 점검 기록이고, 최신 결과는 [최종 접수·검수자 보완](marketing-master-db-intake-reviewer.md)을 참조한다. AI 유보와 두 계정 접근 제한은 유지한다.

점검일: 2026-09-14. 기준은 최초 사용자 요청의 1~6번이며, 이후 설계에서 추가하거나 바꾼 정책을 최초 요구사항으로 간주하지 않았다. 이후 사용자 지시인 ‘AI 연결은 마지막 단계’와 ‘강승억·김하연만 접근’은 유효한 범위 변경으로 반영했다.

## 결론

**최초 요구사항 전체 충족은 아니다.** 기본 관리 흐름은 구현됐지만 AI는 합의에 따라 유보됐고, 비-AI 범위에도 아래 처리 정책 차이와 운영 설정이 남아 있다. 앞선 ‘AI 제외 완료’ 안내는 구현한 보완 목록 기준이었으며, 최초 요청을 모두 충족했다는 뜻으로는 부정확했다.

### 남은 비-AI 항목

1. **오류 Contact를 검수 대상으로 수집하는 처리**
   - 최초 요청: 제출된 Contact의 필수정보 누락·이메일 형식 등을 검사하고 신규/업데이트/중복 의심/확인 필요로 분류해 담당자가 검수한다.
   - 현재: `submissions` API는 회사명·성명·이메일 누락 또는 형식 오류가 있으면 제출 저장 전에 거부한다. Excel에서는 오류 행으로 반환하고, 단건에서는 오류 메시지를 표시한다. 따라서 해당 건이 검수 대기의 ‘확인 필요’로 생성되지 않는다.
   - 필요한 보완: 읽을 수 있는 Contact의 업무상 오류는 원문과 오류 근거를 보존하여 ‘확인 필요’로 수집하고, Master 승인 시 필수값/형식 오류를 차단한다. 손상 파일·잘못된 데이터 구조 같은 접수 불가능 오류는 행별 실패로 구분한다. Excel 부분 성공 기능과 업무 검수 대상 수집을 구분해야 한다.
   - 근거: [제출 API](../frontend/src/app/api/marketing/submissions/route.ts)의 `fieldErrors` 직후 예외 발생, [API 테스트](../frontend/src/lib/__tests__/marketing-submissions-api.test.ts)의 누락 필드 제출 거부 사례.

2. **요청한 담당부서의 실제 검수·승인 권한 설정**
   - 최초 요청: 대외협력·커뮤니케이션실이 검수·승인한다.
   - 현재 운영 조회: 강승억은 관리자(기술·운영부문)로 승인 가능. 김하연은 일반 사용자(사업·전략부문 / 커뮤니케이션팀)이며 명시적 검수자 지정이 없다. 김하연은 접근·제출은 가능하지만 승인할 수 없다.
   - 필요한 보완: 실제 담당 검수 계정을 확정해 검수자로 지정하고 해당 계정의 승인/반려 동작을 확인한다. ‘접근 허용’과 ‘검수자 지정’은 별도 설정이다. 이번 재점검에서는 권한을 임의로 추가하지 않았다.
   - 근거: 운영 `user_profiles`, 활성 `company_directory`, `marketing_reviewers` 읽기 조회 및 `marketing_can_review` 권한 구조.

## 검증 범위와 한계

- 현재 코드와 기존 배포/이관 기록을 대조했다.
- 이번에 제출 API·규칙 검증·검수 화면 테스트 **22개**를 다시 실행해 통과했다. 그중 입력 오류를 거절하는 테스트가 통과한 것은 **현재 동작의 확인**이지 최초 요구를 충족했다는 증거가 아니다.
- 운영의 두 계정 역할·부문·검수자 지정 상태를 읽기 조회했다. 데이터를 수정하거나 검수 권한을 추가하지 않았다.
- AI 실호출과 각 부문 담당자의 업무 인수 테스트는 완료하지 않았다. 부문 전체 확대는 이후의 접근 제한 변경이 있어야 가능하다.

현재 운영 기능의 상세 사용법은 [AI 제외 보완 구현 문서](marketing-master-db-completion.md)에 있다. 최초 요청에 대한 완료 판단은 이 재점검 결과를 함께 적용한다.
