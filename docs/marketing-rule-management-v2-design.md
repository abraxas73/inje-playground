# 관리 규칙 수정 및 Master DB 선택 검증 설계

상태: **구현·운영 반영 완료**. 최신 구현·운영 검증 결과는 [구현 문서](marketing-rule-management-v2.md)를 참고한다. 아래는 구현 전 합의한 설계이며 API 및 작업자 구조의 조정은 구현 문서에 기록했다.

2026-09-14 현재 코드와 운영 DB를 확인해 작성했다. 목표는 원본/추가 업무 규칙을 수정하고, 선택한 규칙으로 전체·필터 결과·선택 Contact를 검사하며, 결과와 후속 검수를 추적하는 것이다. AI 및 Stibee/Eco 외부 동기화는 기존처럼 후속 범위다.

## 1. 현재 문제와 변경 방향

운영 DB는 Master 7,294건, 관리 규칙 16개다. 초기 16개 전부 `protected=true`여서 `RuleManager`가 수정 버튼을 숨기고 `marketing_save_rule`도 변경을 거부한다. 실제로는 **새로 추가한 규칙만 수정 가능**한 구조이며 보호 범위가 과도하다.

또한 현재 검증은 직접 입력한 샘플에 활성 규칙을 적용하는 기능이다. 선택한 규칙만 실행하거나 기존 Master를 대상으로 실행하는 기능은 없다. `builtin` 7개는 기준 설명이며 현재 규칙 엔진에서 개별 검사 결과를 만들지 않는다. 이를 선택 검증에 그대로 사용하면 검사하지 않은 기준이 통과한 것처럼 보일 수 있다.

| 현재 | 변경 설계 |
|---|---|
| 원본 규칙 16개 일괄 잠금 | 업무 규칙은 원본/추가 여부와 무관하게 버전별 수정 |
| 업무 기준과 DB 보호 장치 혼재 | 편집 가능한 업무 기준과 시스템 무결성 제약 구분 |
| 활성 규칙 전체 + 입력 샘플 검사 | 규칙 1개 이상 선택 + 전체/필터/선택 행 검사 |
| 현재 규칙을 즉시 덮어씀 | 적용 버전 보존, 수정본 시험, 새 버전 적용 |
| 실패 항목만 반환 | 통과·미충족·확인 필요·대상 아님·실행 오류를 구분 |
| 과거 Master 재검증 없음 | 실행 이력·진행률·재시도·결과 다운로드 제공 |

## 2. 화면과 사용 흐름

`/marketing`의 기본 진입 화면, 18개 데이터 컬럼, 2줄 헤더, 필터, 원클릭 정렬을 유지한다.

### 규칙 관리

현재 모달 대신 `/marketing/rules`에서 충분한 공간을 확보한다. 기존 **관리 규칙** 버튼을 진입점으로 사용한다.

목록 컬럼은 선택, 규칙명, 검사 대상, 방식, 적용 조건, 미충족 등급, 적용 상태, 현재 버전, 최근 수정자/시각, 수정/이력이다. 검색과 활성/비활성·자동/담당자 확인·원본/추가 필터를 제공한다.

업무 규칙에는 모두 **수정** 버튼을 표시한다. 상세에서는 현재 적용본, 수정본, 변경 차이를 함께 보여준다. 기본 동작은 다음과 같다.

1. 기존 규칙을 수정해 초안 저장.
2. 필요하면 **수정본 시험 검증**으로 Master에 미칠 영향을 확인.
3. **저장 및 적용**으로 새 버전을 적용. 작성자가 직접 수행하며 별도 결재 절차를 추가하지 않는다.
4. 이전 버전으로 되돌릴 때도 기존 기록을 덮어쓰지 않고 복원한 내용을 새 버전으로 생성.

단순 이름/설명 변경에도 변경 사유·버전을 남긴다. 적용 전 시험 검증은 선택 사항이다. 시행 중인 규칙을 수정하는 동안에는 기존 적용본을 계속 사용한다.

### Master에서 검증 시작

Master 표 맨 앞에 행 선택 체크박스를 추가한다. 데이터 컬럼 18개와 Excel 출력 컬럼은 유지하며 선택 체크박스는 UI 전용이다. 상위 헤더 그룹은 기존 데이터 컬럼에만 적용한다.

상단 **규칙 검증**을 누르면 다음 두 가지를 고른다.

| 선택 항목 | 옵션과 동작 |
|---|---|
| 검증 대상 | 전체 Master / 현재 필터 결과 전체 / 직접 선택한 Contact |
| 적용 규칙 | 현재 적용 중인 규칙 중 1개 이상 선택. 전체 선택·검색·개별 선택 지원 |

**현재 페이지 25건**과 **필터 결과 전체 2,149건**을 분명히 구분한다. 헤더 체크박스는 현재 페이지 선택이며, ‘필터 결과 전체 선택’은 별도 동작이다. 페이지/정렬 변경은 선택을 유지하고 필터 변경은 직접 선택을 초기화하며 알린다. 선택 상태는 현재 탭 세션에만 유지한다.

실행 버튼에는 **선택 규칙 3개로 Contact 2,149건 검증**처럼 범위를 표시한다. 규칙 0개·대상 0건이면 실행하지 않는다. 실행 직전 서버에서 권한·ID·규칙 버전을 재확인한다. 실행 이후 화면 필터를 바꿔도 이미 시작된 대상에는 영향을 주지 않는다.

규칙 목록에서 규칙을 선택한 뒤 **선택 규칙으로 검증**을 누르는 역방향 흐름도 제공한다. 같은 실행 설정 화면을 재사용한다.

### 결과 화면

`/marketing/validations`는 실행 이력, `/marketing/validations/{runId}`는 진행/결과 화면이다. 상단에는 대상 조건·확정된 대상 수·선택 규칙/버전·실행자·기준 시각·진행률을 표시한다.

결과는 **Contact별 요약**과 **규칙별 집계** 두 관점으로 제공한다. Contact별 목록에는 DB ID, 회사명, 성명, 결과, 미충족 규칙 수, 대표 사유, 현재 데이터 변경 여부가 있다. 상세에서는 항목값·판정 기준·근거·관련 Contact/회사·규칙 버전을 볼 수 있다.

결과 필터는 규칙, 결과 유형, 오류/경고, 회사·성명·DB ID, 처리 상태다. 결과 다운로드는 현재 결과 필터의 전체 행을 대상으로 한다.

## 3. 규칙의 수정 범위

`protected` 한 개로 수정 여부를 결정하는 구조를 폐지한다. **출처**, **검사 방식**, **수정 가능 속성**을 따로 관리한다.

| 종류 | 수정과 실행 |
|---|---|
| 업무 자동 규칙 | 이름·설명·대상 항목·조건·기준값·심각도·적용 여부를 새 버전으로 수정. 원본 기준도 포함 |
| 담당자 확인 규칙 | 확인 질문·적용 조건·필요한 근거·적용 여부를 수정. 자동 통과를 만들지 않음 |
| 시스템 제약 | 권한, 승인 경로, 고유 ID, 참조 무결성, 원본/감사 이력 보호 등. 별도 영역에 이유를 표시하고 구조적 보호를 해제하는 편집은 제공하지 않음 |
| 운영 원칙 | 자동 판정이 불가능한 설명. 확인 항목으로 전환하거나 실행 대상에서 제외하며 이유를 표시 |

이메일 고유 인덱스 등 실제 DB 제약과 충돌하는 규칙 설정은 적용 전에 이유를 명시해 거절한다. ‘규칙에서는 허용으로 바뀌었는데 다른 코드에서 조용히 차단’하는 상태를 만들지 않는다.

중요한 구현 변경: 회사명/성명/이메일 필수, 이메일/날짜 형식 등 업무 검사는 현재 `fieldErrors`, Form 필수 표시, 승인 RPC에 중복되어 있다. 편집 가능한 업무 기준은 **동일한 DB 규칙 정의**를 사용하도록 함께 정비해야 한다. 단순히 `protected=false`로 변경하는 것만으로 완료 처리하지 않는다. DB 구조상 필수인 조건은 편집 화면에서 시스템 제약으로 명시한다. 초기 적용본의 동작은 그대로 이관하며, 사용자가 새 버전을 적용할 때 업무 기준이 바뀐다.

기본 검사 방식은 기존 필수값·이메일·날짜·허용값·금지값·최대 길이·담당자 확인을 유지한다. 선택 대상은 화면의 18개 필드와 회사 확인 상태까지 명시적으로 정의한다. 임의 코드/SQL 실행은 허용하지 않는다. 데이터 간 비교는 별도 검증기로 제공한다.

## 4. 기존 관리기준의 검증 가능성

| 기준 | 일괄 검증에서의 처리 |
|---|---|
| 회사명·성명·이메일 필수/형식, 최종확인일 | 대상 Contact의 실행 당시 값으로 자동 검사 |
| DB ID·이메일 중복 | 데이터 집합 비교 검사. ID/이메일 DB 제약 자체는 유지 |
| 회사명+성명 중복 가능성 | 표준 회사·승인 별칭 기준으로 후보 그룹 반환. 동일 인물 확정/병합 없음 |
| 회사명 표준화 | 원문과 현재 표준명·승인 별칭을 대조해 미연결/불명확 후보 표시. 알려진 원문 표기 차이만으로 오류 판정하지 않음 |
| 회사·기관 분류 | 미분류/확인 보류, 같은 회사로 보이는 표기의 상이한 분류 후보 검사. 별도 법인 가능성은 확인 필요 |
| 회사 단위 분류 관리 | 회사 관계·분류 연결 무결성 검사. 승인된 분류 변경과 과거 원본 분류의 차이는 오류로 간주하지 않음 |
| 원본 추적 | 이관 배치/원본 행 또는 제출·승인 이력 연결 확인. Form 제출에 Excel 시트명을 강제하지 않음 |
| 실제 관리 가능한 Contact, 확인된 정보 | 담당자 확인 필요. 소속명 문자열이 있다는 것만으로 실재 확인 완료 처리하지 않음 |
| 발송 유효성 | 외부 이력 미연계 상태를 명시하고 담당자 확인 필요. 이메일 형식 검사를 수신동의/발송 유효성으로 대체하지 않음 |
| Eco 확정 정보 | Eco 값이 있으면 담당자 확인 필요. 없으면 대상 아님 |
| 기업·공공기관 등의 포괄 범위 | 운영 원칙으로 설명. 자동 실행 대상으로 제시하지 않음 |
| 담당자 이동·퇴사 시 업데이트 | 변경 요청/검수 운영 절차. 근거 데이터 없이 이동·퇴사를 자동 추정하지 않음 |

기존 `builtin` 7개를 모두 가짜 자동 규칙으로 취급하지 않는다. 실제 검증기, 담당자 확인, 실행하지 않는 운영 원칙으로 분리한다. 초기 목록 16개와 새 버전의 규칙은 원본 행/기존 코드로 추적한다. 복합 기준을 여러 검사로 나누면 파생 관계를 기록한다.

## 5. 검증 대상과 비교 범위

**검사 대상**과 **비교 대상**을 분리한다. 예를 들어 10명을 선택해 중복 검증하더라도 비교는 실행 당시 전체 Master를 기준으로 해야 나머지 7,284명과의 중복을 찾을 수 있다. 결과의 주 대상은 선택한 10명으로 유지하고, 대상 밖 Contact는 관련 후보로 표시한다.

중복 후보에서 자기 자신의 Contact ID는 제외한다. 빈 이메일·빈 성명끼리 같은 값이라고 묶지 않으며, 비교에 필요한 값이 없으면 필수값 규칙과 구분해 해당 비교는 대상 아님으로 표시한다. 회사명·이메일·성명의 비교 키는 기존 접수/승인과 동일한 정규화 함수를 사용한다.

회사 단위 기준은 대상에 포함된 회사마다 한 번 검사한 뒤 소속 대상 Contact에 연결한다. 회사 단위 문제 수와 영향 Contact 수를 구분하고, 대상 밖 소속 Contact의 영향 수를 별도로 알려준다.

실행 생성 시 **규칙 버전·규칙 설정·대상 Contact ID/버전/값·회사 버전/표준값·전체 비교용 최소 정보**를 함께 고정한다. 이관 원본의 수정은 없다. 생성은 동일 DB 스냅샷을 사용하는 단일 SQL 문/CTE로 원자적으로 수행하며, 여러 HTTP 조회를 연결해 만든 시점을 기준으로 삼지 않는다.

중복 비교용 전체 정보에는 필요한 ID·버전·이메일 키·회사 키·성명 키 등을 저장한다. 전체 Contact의 모든 필드를 중복 복사하지 않는다. 선택 대상의 원본 입력/회사 기준/출처는 해당 규칙이 필요로 하는 범위에서 보존한다.

규칙을 수정하거나 Contact가 승인 변경되더라도 진행 중인 실행은 고정된 기준으로 끝난다. 결과에는 **현재 데이터가 이후 변경됨**을 표시하고 최신 상태 재검증을 제공한다. 상대 날짜 규칙을 확장할 경우에도 실행 기준 시각과 한국 날짜를 고정한다.

## 6. 결과와 후속 처리

검사 결과는 다음 다섯 가지로 고정한다.

| 결과 | 의미 |
|---|---|
| 통과 | 선택된 자동 규칙을 실제 실행해 충족 |
| 미충족 | 자동 규칙의 조건/기준에 맞지 않음. 오류/경고 등급 별도 표시 |
| 확인 필요 | 사람이 자료나 사실관계를 확인해야 함 |
| 대상 아님 | 해당 규칙의 적용 조건에 해당하지 않음 |
| 실행 오류 | 데이터/검증기 오류로 판정하지 못함. 재시도 대상 |

검증기를 연결하지 못한 선택 규칙은 실행 전에 막는다. 실행 중 검증기 오류를 ‘통과’ 또는 ‘대상 아님’으로 숨기지 않는다. 모두 대상 아님이면 Contact를 통과로 집계하지 않는다. 일부 규칙만 실행한 결과에 ‘Master 전체 정상’ 같은 표현을 사용하지 않는다.

진행률은 처리한 Contact 수로 계산한다. 요약은 Contact 수와 규칙 결과 건수를 별도 표시한다. 한 Contact에서 오류 3개가 나와도 오류 Contact는 1명이다. 실행 오류가 있는 Contact는 미완전 검증으로, 그 외에는 오류 → 경고/확인 필요 → 통과 → 대상 아님 순으로 대표 결과를 표시한다.

원본 검사 결과는 변경하지 않는다. 담당자는 별도의 처리 이력에 확인 근거·처리자·시각을 남긴다. 수동 확인을 마쳐도 과거 자동 판정이 바뀌지 않는다. 확인 완료의 근거는 Contact/회사/규칙 버전과 연결하며, 관련 버전이 바뀌면 다시 확인해야 한다.

**변경 요청 작성**은 기존 Form을 열고 실행 ID/결과 ID를 출처로 연결한다. 사용자가 값을 검토·수정해 제출하고 기존 승인 흐름을 거친다. 여러 결과가 같은 Contact에 있으면 한 변경 요청에 묶는다. 재시도나 두 번 클릭으로 동일 변경 요청이 중복 생성되지 않도록 요청 키를 사용한다.

일괄 검증 자체는 Master 수정·병합·삭제·최종확인일 갱신·대량 승인·자동 검수 요청 생성을 하지 않는다. 검증에서 규칙을 일부만 골랐어도 실제 승인에는 현재 적용 중인 승인 규칙 전체와 시스템 제약을 다시 적용한다.

## 7. 비동기 실행

7,294건을 브라우저 요청 하나가 끝날 때까지 기다리거나, 탭이 열려 있을 때만 순차 호출하는 구조는 사용하지 않는다. 작업을 DB에 저장하고 서버 작업자가 나눠 처리한다. 화면은 진행 상태만 조회하므로 탭을 닫아도 계속된다.

운영 DB의 `pg_cron` 설치를 확인했고 저장소에 `pg_cron`/`pg_net` 기반 작업 호출이 있다. 이를 따라 작업 시작 시 즉시 서버 작업자를 호출하고, 주기적인 작업자가 누락/중단 작업을 회수하는 방식을 사용한다. 새 외부 큐 서비스나 AI 호출을 필수로 추가하지 않는다.

- 초기 처리 단위: Contact 200건. 규칙 수/데이터량별 부하 측정으로 조정한다.
- 실행 상태: 대기 → 실행 중 → 완료 / 일부 실행 오류 / 취소됨 / 실패. 취소 요청 중 상태는 별도 표시한다.
- 작업자는 잠금과 만료 시각이 있는 실행 권한을 획득한다. 동시 작업자가 같은 조각을 중복 확정하지 못하게 한다.
- 결과 저장과 처리 완료 표시는 같은 트랜잭션으로 커밋한다. `(실행, Contact, 규칙 버전)` 고유 키와 실행 권한 세대로 재실행/늦은 응답의 중복 반영을 방지한다.
- 재시도는 실패/미처리 항목만 같은 고정 데이터로 실행한다. 최신 데이터로 다시 검증은 새 실행을 만든다.
- 취소 요청 후 새 조각을 시작하지 않는다. 진행 중 조각의 종료를 확인한 후 취소 완료로 표시하고 이미 확정된 결과는 보존한다.
- 중복 비교는 이메일/회사·성명 키 인덱스로 처리하며 Contact마다 전체 Master를 반복 조회하지 않는다.
- 실제 처리 속도·DB 부하는 배포 전 7,294건 규모로 측정한다. 아직 측정하지 않은 완료 시간을 보장하지 않는다.

## 8. DB 구조

| 구조 | 역할과 핵심 필드 |
|---|---|
| `marketing_rules` | 규칙 식별자/출처/분류/현재 적용 버전 포인터. 삭제 대신 비활성/보관 |
| `marketing_rule_versions` | 규칙 ID, 버전, 상태, 이름/설명, 대상 종류, 검사 방식/설정, 등급, 수정 사유, 작성자/시각, 내용 해시. 적용된 버전 불변 |
| `marketing_rule_history` | 기존 이력 보존. 초안 저장/새 버전 적용/복원/비활성 이벤트 연결 |
| `marketing_validation_runs` | 요청 키, 대상 방식/필터/선택 정보, 기준 시각, 선택 버전/정의, 엔진 버전, 실행자, 상태, 집계, 작업자 실행 권한/만료 시각 |
| `marketing_validation_targets` | 실행 ID + Contact ID, 당시 DB ID/Contact 버전/값/회사 기준, 처리 상태, 정렬용 실행 순번 |
| `marketing_validation_reference` | 실행 시점 전체 비교용 최소 정보. `(run_id,email_key)`, `(run_id,company_key,name_key)` 인덱스 |
| `marketing_validation_results` | 실행/대상/규칙 버전, 판정, 등급, 실제값/기준/근거, 관련 대상. 동일 결과 키 중복 금지 |
| `marketing_validation_followups` | 결과 또는 묶인 Contact에 대한 확인 근거, 담당자, 처리 상태, 연결된 변경 제출/승인, 시각 |

규칙 정의는 실행에 한 번 보존하고 결과마다 전체 정의를 중복 저장하지 않는다. 전체 7,294건 × 16개를 실행하면 최대 116,704개 결과 조합이 생길 수 있으므로 결과는 DB 페이지네이션을 사용한다. 결과 필터 인덱스는 `(run_id,outcome,severity)`와 대상/규칙 키를 기준으로 검증한다.

새 규칙 버전, 실행 스냅샷, 원본 판정은 사용자 직접 UPDATE/DELETE를 허용하지 않는다. 현재 접근 가능한 두 계정 정책을 유지하고, 실행/수정/처리는 검수 담당자 권한을 요구한다. 작업자용 함수는 일반 사용자 호출을 차단하고 실행에 저장된 범위만 처리한다. 다른 관리자에게 권한이 확장되지 않도록 페이지·API·RLS를 함께 적용한다.

개인정보를 포함한 대상/결과는 기존 Master와 같은 접근 수준으로 관리한다. 임의 공개 링크나 외부 전송을 추가하지 않는다. 보관 기간은 기존 정책을 따르고, 새 자동 삭제 정책은 이 변경에서 만들지 않는다.

## 9. API와 공통 검증기

| 경로/작업 | 역할 |
|---|---|
| `GET /api/marketing/rules` | 규칙·현재 버전·수정 가능 속성 조회 |
| `POST /api/marketing/rules` | 새 업무 규칙/초안 생성 |
| `PATCH /api/marketing/rules/{id}` | 기준 버전을 확인해 수정본 저장 |
| `POST /api/marketing/rules/{id}/publish` | 새 버전 적용. 호환성 검사와 변경 사유 기록 |
| `GET /api/marketing/rules/{id}/versions` | 적용/이전 버전 및 변경 차이 조회 |
| `POST /api/marketing/validation-runs` | 규칙 버전과 전체/필터/ID 범위를 받아 실행 생성·원자적 스냅샷 확보 |
| `GET /api/marketing/validation-runs` | 실행 이력 |
| `GET /api/marketing/validation-runs/{id}` | 진행률·요약 |
| `GET /api/marketing/validation-runs/{id}/results` | 필터/정렬/페이지별 결과 |
| `POST .../{id}/cancel`, `POST .../{id}/retry` | 취소, 동일 기준 실패 항목 재시도 |
| `POST .../{id}/followups` | 담당자 확인 기록, 검토 후 변경 요청 연결 |
| `GET .../{id}/export` | 선택 실행의 필터 결과 전체 Excel 다운로드 |

현재 단건 `marketing_validate_rules`를 **명시적인 규칙 버전 집합 + 입력/비교 컨텍스트 + 기준 시각**을 받는 공통 검증기로 분리한다. Form/Excel 접수, 승인, 샘플 시험, Master 일괄 검증이 같은 검사 코드를 사용한다. 정책 선택은 호출자가 임의의 JSON으로 위조하지 못하도록 서버가 검증한다.

규칙 초안 저장과 적용은 기준 버전을 확인하고, 다른 사용자가 먼저 변경했다면 `409`로 차이를 반환한다. 검증 실행 생성에도 요청 키를 사용해 이중 클릭으로 같은 실행이 생기지 않게 한다. 실행 설정 중 선택 규칙이 변경되거나 비활성화되면 최신 목록을 안내하고, 다른 버전으로 조용히 대체해 실행하지 않는다. 수정본 시험은 지정한 초안 내용을 고정한 별도 시험 실행으로 기록하며 실제 승인 정책을 바꾸지 않는다.

샘플 입력은 데이터 집합 비교를 할 충분한 컨텍스트가 없으면 ‘이 시험에서 실행 불가’로 표시한다. Master 일괄 검증에서는 고정된 전체 비교 정보로 실제 실행한다. 승인에서는 선택 실행 결과가 아닌 현재 승인 정책과 최신 데이터로 검사한다.

## 10. 결과 Excel

기존 Master 다운로드와 검증 결과 다운로드를 구분한다.

- `검증 결과`: DB ID, 회사명, 성명, 대상 필드, 규칙명/버전, 판정/등급, 검사 당시 값, 기준/근거, 현재 데이터 변경 여부, 후속 처리 상태.
- `실행 정보`: 기준 시각, 실행 범위/필터, 확정 대상 수, 규칙 목록/버전, 결과 집계, 완료/부분 실행 여부.
- 결과 다운로드는 현재 페이지 제한을 따르지 않고 결과 필터 전체를 내린다. 대량 결과는 서버에서 나눠 읽고 스트리밍 작성한다.
- 부분 실행 결과도 받을 수 있으나 미처리/실행 오류 수를 명시한다. 문자열을 수식으로 실행하지 않으며 ID/연락처의 앞자리 0을 보존한다.

## 11. 구현 순서

1. **규칙 편집 정상화**: 원본/추가 업무 규칙의 수정, 버전/차이/복원, 세부 수정 가능 속성, 기존 하드코딩 검증 정리. 출처를 이유로 일괄 잠그지 않는다.
2. **공통 검증기 정비**: 선택 버전 실행, 다섯 가지 결과, 데이터 집합/회사 단위 검사, 운영 원칙 처리. 기존 접수/승인 동작 회귀 검사.
3. **검증 대상 선택·서버 작업**: 전체/필터/행 선택, 대상/규칙 고정, DB 작업자, 진행률/취소/재시도.
4. **결과와 후속 검수**: 결과 필터·규칙 집계·버전 비교·결과 Excel·수동 확인·기존 변경 Form 연결.

이 네 단계가 모두 필요하다. 1단계만 완료하고 ‘전체/일부 Master 선택 검증 구현 완료’라고 보고하지 않는다. 기존 규칙/검증/승인 이력은 보존하며 과거 기록에 새 규칙의 검증 결과를 소급해 채우지 않는다.

## 12. 완료 기준

1. 원본에서 온 이메일/날짜/담당자 확인 규칙을 실제 수정하고 새 버전 적용 후 동일한 입력의 결과가 달라진다. UI·API·SQL 간 모순 없음.
2. 추가 규칙 수정·비활성·복원 이력이 남고, 동시 편집 시 마지막 저장이 다른 변경을 덮어쓰지 않는다.
3. ‘Eco 여부=Y일 때 Eco ID 필수’ 하나만 선택해 전체·필터·직접 선택에 각각 실행하며 선택하지 않은 규칙은 검사되지 않는다.
4. 25건을 초과하는 필터 전체 선택에서 모든 대상이 검사된다. 대상 10명만 골랐어도 전체 Master에 있는 중복 후보를 찾는다.
5. 회사 단위 판정과 영향 Contact 수가 중복 없이 집계된다.
6. 실행 도중 규칙/Contact/회사 정보 변경, 탭 닫기, 작업자 종료가 있어도 기존 실행의 기준과 완료/미처리 수가 정확하다.
7. 수동 확인·조건 비해당·검사 오류가 통과로 표시되지 않는다. 선택하지 않은 규칙까지 검증됐다고 표시하지 않는다.
8. 재시도/이중 클릭/작업자 중복 실행에서 결과·변경 요청이 중복 생성되지 않는다. 취소 후 미처리 자료를 완료로 집계하지 않는다.
9. 검증만 실행했을 때 Master의 값·버전·최종확인일은 변하지 않는다. 수정 요청과 승인은 기존 흐름을 통해서만 반영된다.
10. 결과 화면과 결과 Excel의 범위·규칙 버전·순서·건수가 일치한다. 다른 관리자와 비로그인 사용자는 조회·실행·수정을 할 수 없다.
11. 운영 적용 전 7,294건/16개 기준의 데이터 크기·실행시간·DB 부하·재시작·진행률을 실제 측정하고 기록한다.
