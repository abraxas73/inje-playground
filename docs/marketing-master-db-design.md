# 마케팅 Master DB 관리 — 1차 구현 명세

상태: AI 연결을 제외한 1차 요구사항의 마지막 두 보완 항목(오류 Contact 수집·담당 검수자 지정)을 처리하고 운영 반영·검증을 완료했다. [최신 구현 및 검증 결과](marketing-master-db-intake-reviewer.md)를 참조한다. AI는 사용자 지시로 마지막 단계에 남겨두었다.

## 원본 분석

분석 파일: `INNOGRID Master DB_v1.5 (1).xlsx` (2026-09-14 확인).
원본 파일을 수정하지 않고 XLSX 내부 XML의 저장된 값을 읽었다.

- `01_Master_DB`: 3행 헤더, 4행 이후 비어 있지 않은 Contact **7,294건**.
- 회사명 누락 **732건**, 성명 누락 **434건**, 이메일·DB ID 누락 **0건**. 누락 건수는 서로 중첩될 수 있다.
- 이메일 앞뒤 공백 제거 및 소문자 변환 기준 중복 그룹 **0개**.
- DB ID 중복 **0개**. 회사명 앞뒤 공백 제거·대소문자 통일 기준 비어 있지 않은 회사명 **2,826개**, 이 기준의 동일 회사명 내 분류 충돌 **0개**. 별칭·법인 동일성 검증을 마친 회사 수는 아니다.
- 기본 이메일 정규식 `[^\s@]+@[^\s@]+\.[^\s@]+` 불일치 **0건**. 발송 가능성이나 수신동의 검증 결과는 아니다.
- 분류: IT기업 2,149 / 솔루션·제품사 1,486 / 공공기관 1,126 / 확인 필요 913 / 기타 499 / 교육·연구 496 / 제조사 251 / 금융 140 / 협회·단체 127 / 언론 107.
- `00_대시보드`, `02_관리기준`, `03_대시보드계산`은 Contact로 가져오지 않는다. `02_관리기준` 3~14행은 이후 DB 관리 규칙으로 등록했으며 [실행 방식과 원본 대조](marketing-master-db-rules.md)를 참조한다.
- 사용자 설명의 원본 10,766건은 제공 파일에서 별도의 원본 목록으로 검증하지 못했다.

## 구현 위치와 범위

기존 Next.js 앱의 `/marketing` 메뉴로 추가한다. 기존 로그인, 페이지 접근 권한, 상단 내비게이션, Pretendard와 Innogrid CI 색상, shadcn UI를 재사용한다.

1차 범위는 신규·변경 Contact 입력 및 Excel 일괄 제출, 기존 Master 비교, 회사 표준명·분류 추천, 담당자 검수·승인, 반영 이력이다. Stibee 발송결과, Eco Partner 동기화, 월간 리포트는 후속 범위다. 기존 Eco 필드는 그대로 보존한다.

## 화면

### Master DB

- 회사명·성명·이메일 통합 검색, 분류/관리부서/정비 필요 필터, 서버 페이지네이션.
- 기본 진입 화면은 Master DB이며 원본 18개 컬럼과 5개 그룹/2줄 헤더를 표시한다. 표 내부 가로 스크롤을 지원한다.
- 상세에서 연락처, 원본출처·원본시트, Eco 5개 필드, 비고 및 변경 이력 확인.
- 수정은 변경 제출 화면으로 이어지며 Master 직접 수정 버튼은 제공하지 않는다.
- 기존 누락 레코드는 숨기거나 삭제하지 않고 ‘기존 데이터 정비 필요’ 표시.

### Contact 제출

- 단건 폼과 Excel 양식 업로드. 회사명·성명·이메일을 신규 등록 필수값으로 사용.
- 입력: 변경 대상 DB ID(선택), 회사명, 성명, 소속부서, 직책, 이메일, 연락처, 확인일, 유입출처, 비고.
- 제출자의 계정·현재 부문은 서버에서 확정하여 기록한다. 회사의 소속부서와 사내 제출부문을 구분한다.
- 업데이트에서 빈칸은 ‘기존값 유지’. 값을 지울 때는 명시적 삭제 표시가 필요하다.
- 업로드 미리보기에서 시트, 컬럼 매핑, 총 행수, 행별 오류를 보여준 후 제출한다.
- 제출에 성공한 행만 검수 대상으로 만들며 오류 행은 행번호와 원인을 제공한다. 부분 성공 여부를 명확히 표시한다.
- 본인 제출의 검증 중/검수 대기/반려/반영 상태 확인 및 반려 사유에 따른 재제출.

### 검수 대기 (핵심 시안)

- 신규 등록 / 기존 정보 업데이트 / 중복 의심 / 확인 필요 필터와 제출부문 필터.
- 좌측 대기 목록, 우측 선택 건의 기존값 / 제출값 / 최종 반영값 비교.
- 비교 대상 DB ID와 일치 근거, 회사 표준명 후보, 분류 근거, 미해결 항목 표시.
- AI 추천과 결정적 규칙 검사를 분리 표시하고 AI 실패를 정상 검증처럼 표현하지 않는다.
- 담당자 수정, 대상 Contact 선택, 회사·기관 선택, 사유 입력, 승인 또는 반려.
- 승인 전 변경 필드와 반영 대상 요약. 필수정보 오류나 미해결 충돌이 있으면 승인 불가.
- 일괄 승인은 첫 버전에서 제외하여 모호한 레코드의 무심코 승인 방지.

### 회사·기관 / 변경 이력

- 표준회사명, 승인된 별칭, 분류, 소속 Contact 수, 확인 상태 관리.
- 유사 이름을 그룹으로 제시해도 회사 ID를 자동 병합하지 않는다.
- 회사 분류 변경 시 영향 Contact 수를 보여주고 담당자가 승인한다.
- 이력: 제출자·부문, 승인자, 시간, 대상 ID, 변경 전후값, 사유, 원본 파일/시트/행.

## 비교·검증 정책

판정 우선순위는 필수정보·형식·상충 오류 → 복수 후보 및 인물 충돌 → 단일 확정 대상 업데이트 → 신규 후보 순서다. 모든 경우 검수 승인 전 Master 반영은 없다.

| 조건 | 판정 / 처리 |
|---|---|
| 필수정보 누락, 이메일 기본 형식 오류, 지정 DB ID 없음 | 확인 필요, 등록/변경 승인 차단 |
| 지정 DB ID와 이메일이 서로 다른 기존 레코드를 가리킴 | 확인 필요, 대상 선택 및 재검증 |
| 이메일 일치 + 성명·회사 충돌 없음 | 기존 정보 업데이트 후보. 모든 필드가 같으면 ‘변경 없음’으로 종결 가능 |
| 이메일 일치 + 성명 또는 회사 충돌 | 중복 의심. 대표메일 공유·이직 등 확인 후 대상 확정 |
| 회사 ID + 성명 일치, 이메일 다름 | 중복 의심. 단순 신규 등록으로 처리하지 않음 |
| 여러 기존 Contact 후보 | 중복 의심, 후보 선택 요구 |
| 일치 후보 없음 + 회사 확정 + 필수정보 정상 | 신규 등록 후보 |
| 회사·분류가 불확실 | 확인 필요. 담당자가 근거와 함께 확정 |

- 이메일 비교용 키만 trim/lowercase 한다. 원문은 유지한다. Gmail 점·플러스 제거처럼 서로 다른 주소를 합치는 정규화는 하지 않는다.
- 제출 배치 내부 중복과 다른 미처리 제출 중복도 함께 검사한다.
- 회사명 검색 키는 공백·법인 표기 차이를 후보 검색에 활용한다. 검색 키 일치만으로 동일 법인을 확정하지 않는다.
- 기존 승인 별칭이나 확정 회사 ID가 있으면 표준회사명과 회사 분류를 추천값으로 적용한다.
- 기존 회사명에 서로 다른 분류가 있으면 다수결하지 않고 회사 단위 정비 항목으로 만든다.
- 일반 이메일 도메인은 회사 식별 증거로 사용하지 않는다. 기업 도메인도 계열사 공유 가능성이 있으므로 단독 확정 근거로 사용하지 않는다.
- 신규 회사는 회사명·도메인을 근거로 기존 10개 분류 중 추천하되, 판단이 어려우면 ‘확인 필요’를 반환한다.
- 현재 ‘확인 필요’ 분류를 승인된 업종처럼 취급하지 않는다. 담당자는 회사 식별이 확정된 경우에도 분류를 보류 상태로 명시적으로 남길 수 있다.

## AI 경계

- 결정적 중복·형식·필수값 검증은 코드로 수행한다. AI는 회사명 후보 비교와 분류 추천, 근거 요약을 보조한다.
- AI 입력은 회사명·이메일 도메인 및 선별된 기존 회사 후보로 최소화한다. 원본 Excel 전체를 전달하지 않는다.
- AI 결과는 스키마 검증: 허용 분류, 제공된 후보 ID, 근거, 불확실 사유. 입력에 없던 회사 ID를 생성하지 못한다.
- 입력 텍스트의 지시문은 데이터로만 취급한다. AI 도구에는 Master 쓰기 권한을 부여하지 않는다.
- 실패·시간 초과·잘못된 출력은 ‘AI 추천 실패 / 담당자 확인 필요’로 기록하며 재시도 가능하다.
- 검증 규칙 버전, 모델명, 생성시각, 추천 결과와 담당자 최종 결정을 별도로 남긴다.

## 데이터 모델 및 승인 트랜잭션

아래는 최초 설계안이다. 구현된 테이블/RPC는 `docs/sql/2026-09-14-marketing-master.sql`을 기준으로 한다. 원본 배치·행과 감사 이력은 별도 테이블, 최신 추천 결과는 제출 JSON에, 생성시각을 포함한 모든 후속 검증 결과는 `marketing_validations`에 누적 저장한다. 별칭은 별도 테이블 대신 회사의 배열과 회사 변경 감사 기록으로 관리한다.

- `marketing_organizations`: UUID, 표준명, 분류, 분류 확인 상태, 버전.
- `marketing_organization_aliases`: 원문 별칭, 비교키, 회사 ID, 승인 이력. 모호한 키는 여러 후보로 유지.
- `marketing_contacts`: 내부 UUID, 원본 DB ID(불변), 회사 ID(nullable: 기존 미확인 자료), 성명·부서·직책·이메일·연락처, 기존 Eco 필드, 최종확인일, 비고, 버전.
- `marketing_import_batches` / `marketing_source_rows`: 파일 해시·파일명·시트·행번호·원문 18개 필드, 업로더, 입력 시각. 원본 추적은 별도 보존.
- `marketing_submissions`: 원문 입력, 제출자·부문 스냅샷, 의도(신규/변경), 명시적 삭제필드, 대상 ID, 기준 버전, 상태.
- `marketing_validations`: 추천 종류·후보·이유·오류·추천 회사와 분류·검증 버전.
- `marketing_review_events`: 변경 전후 스냅샷, 승인/반려 사유, 행위자, 시각. 추가 기록만 허용.
- `marketing_reviewers`: 승인 권한을 가진 계정 목록. 페이지 접근 권한과 승인 권한을 분리.

승인은 서버에서 재인증하고 검수자 권한을 검사한다. 단일 DB 트랜잭션 안에서 제출과 대상의 버전을 잠그고, 최신 Master 및 배치 중복을 재검증하고, 최종값 제약을 확인한 뒤 회사/Contact 변경·감사 이력·제출 상태를 함께 저장한다. 기준 버전이 달라지면 409와 재검증 요구를 반환한다. 동일 승인 요청 재전송은 중복 레코드를 생성하지 않는다. 클라이언트에서 직접 Master UPDATE는 불가하며 RLS/서버 권한으로 차단한다.

## 최초 이관

일반 신규 Contact 제출과 최초 Master 이관은 다른 경로다. 최초 이관은 기존 자료 보존을 위한 별도 관리자 작업으로 미리보기와 건수 대조 후 확정한다.

1. 헤더 18개 및 시트 이름 확인, DB ID 유일성·행수 검증. 수식은 실행하지 않는다.
2. 원본 7,294건과 18개 필드를 손실 없이 저장하고 파일·시트·행번호를 연결한다.
3. 회사명/성명 누락을 보존하면서 정비 대상으로 표시한다. 회사가 불명확하면 회사 FK는 null.
4. 기존 회사명·분류 충돌을 검출하여 목록을 만들고, 임의 표준화·병합 없이 이관한다.
5. 동일 파일 해시의 재이관은 차단한다. 일부 실패 시 전체 이관을 롤백하거나 명시적으로 재개 가능한 배치를 사용한다.
6. 운영 원본 Excel은 덮어쓰지 않는다. 발송동의·수신거부는 현재 파일만으로 확정하지 않는다.

## 수용 테스트

- 신규·업데이트·중복 의심·확인 필요 및 AI 실패가 각각 올바른 상태와 근거를 갖는다.
- 동일 이메일이지만 다른 사람인 경우 자동 업데이트되지 않는다.
- DB ID와 이메일의 대상이 충돌하면 승인이 막힌다.
- 회사명 변형은 후보를 제공하되 별도 법인을 자동 병합하지 않는다.
- 같은 회사의 분류는 회사 테이블에서 일관되게 조회된다.
- 미승인 제출, 반려 제출, 비검수자의 승인 시도는 Master를 변경하지 않는다.
- 빈 업데이트 필드가 기존값을 지우지 않으며 명시적 삭제만 적용된다.
- 두 검수자의 동시 승인, 오래된 대상 버전, 배치 내 중복, 승인 재전송을 안전하게 처리한다.
- 가져오기 전후 건수·DB ID·원문 필드를 대조하고 감사 기록에서 출처 및 변경 전후를 추적한다.
- API 실패, 빈 결과, 로딩, 모바일 비교 화면, 키보드 폼 접근을 확인한다.

## 후속 운영 설정

실제 검수 담당 계정 및 제출부문 매핑은 기존 사내 회원정보를 연결한다. 운영 배포 전 지정된 담당자에게만 승인 권한을 부여한다. Stibee/Eco 연동이나 발송 기능은 이번 화면의 활성 기능으로 표시하지 않는다.
