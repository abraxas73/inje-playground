# 마케팅 Master DB — 설계 대비 구현 점검

> 후속 상태: 이 문서는 **보완 전 발견 사항의 기록**이다. 이후 사용자 요청에 따라 AI 외 항목을 보완했다. 현재 구현과 검증 결과는 [AI 제외 1차 보완 구현](marketing-master-db-completion.md)을 참조한다. 아래 미구현/부분 표시는 최초 점검 당시 상태다.

점검일: 2026-09-14. 대상: [1차 구현 명세](marketing-master-db-design.md), 현재 작업공간 코드, 운영 DB의 검수자 권한 변경 함수.

## 결론

**설계 문서의 모든 항목이 구현된 것은 아니다.** 단건/Excel 제출 → 규칙 검증 → 검수 → 승인/반려 → Master 반영의 기본 흐름과 최초 데이터 이관은 구현돼 있다. 다만 AI 실연결, 일부 화면 기능, 검증 이력 보존, 승인 직전 재검사 등이 남아 있다. 따라서 현재 상태는 **핵심 흐름을 배포한 제한 운영 버전**이며 설계 전체 완료로 인수하면 안 된다.

이 점검에서 기능을 추가하거나 운영 데이터를 변경하지 않았다. 기존 테스트 통과 기록과 코드를 대조했고, 아래 권한 예외는 운영 함수 정의도 읽어 확인했다. 이번 점검에서 전체 수용 테스트를 다시 실행한 것은 아니다.

상태 기준: **완료**는 해당 기능의 구현 확인, **부분**은 일부 동작 또는 검증이 부족, **미구현**은 대응 기능 없음, **연결 대기**는 코드만 있고 실제 서비스 호출 검증 전, **변경 구현**은 설계와 다른 구조/정책이다.

## 요구사항별 대조

| 설계 항목 | 상태 | 실제 구현 및 차이 |
|---|---|---|
| 기존 앱 `/marketing`, 로그인·내비게이션 연계 | 완료 | 홈 카드·메뉴·페이지/API 권한 연결. 현재 사용자 지시로 강승억·김하연만 접근하는 제한 운영 |
| Master 회사명·성명·이메일 검색, 분류·정비 필터, 서버 페이지네이션 | 완료 | 25건 단위 검색. DB ID 검색도 지원 |
| Master 관리부서 필터 | 미구현 | 검수 큐의 제출부문 필터는 있지만 Master의 내부 관리부서 필터는 없음 |
| Master 기본 표, 연락처·원본·Eco 상세, 변경 제출 진입 | 완료 | 상세 조회와 변경 제출을 제공하며 Contact 직접 수정은 승인 경로를 거침 |
| Contact 상세에서 해당 Contact의 변경 이력 | 미구현 | 상세 API는 Contact와 최초 원본 행만 반환. 전체 변경 이력 탭은 별도 존재 |
| 기존 누락 자료 보존 및 정비 필요 표시 | 부분 | 원본 누락 유지, 정비 필터·누락 지표·일부 셀 표시 있음. 행 단위의 통일된 ‘기존 데이터 정비 필요’ 표시는 없음 |
| 단건 제출, 입력 필드, 제출자·현재 부문 서버 확정 | 완료 | 원본/Eco를 포함한 입력, 계정과 사내 디렉터리 기반 부문 기록. 매핑 없으면 소속 미확인 |
| 신규 회사명·성명·이메일 필수 | 변경 구현 | 누락이 있어도 ‘확인 필요’로 제출 가능. 필수값은 최종 승인 시 차단 |
| 업데이트 빈칸 유지 / 명시적 삭제 | 완료 | 단건 폼에서 삭제 체크. Excel은 빈칸 유지, 삭제는 단건 폼 사용으로 안내 |
| Excel 양식·시트·인식 컬럼·행별 오류 미리보기 | 완료 | 정해진 헤더 자동 인식, 최대 50건. 임의 양식의 컬럼 매핑 편집 기능은 없음 |
| Excel 성공 행만 제출, 오류 행 분리, 부분 성공 결과 | 변경 구현 | 정상/필수값 오류 행을 함께 검수 제출. DB ID 미존재 등의 요청 오류는 전체 실패. 행별 성공/실패 결과와 부분 재시도 기능 없음 |
| 본인 제출 상태 및 반려 후 재제출 | 부분 | 검수 대기·반려·반영 완료와 수정 재제출 있음. ‘검증 중’은 버튼 로딩이며 저장된 상태가 아님. 반려 사유가 제출 상세에 직접 표시되지 않음 |
| 검수 결과 4종·제출부문 필터, 좌우 목록/비교 화면 | 완료 | 기존값·제출값·최종값, 대상 후보, 검증 근거 표시 |
| 규칙 검사와 AI 상태 분리, 실패 표시와 재시도 | 완료 | 미설정/실패를 별도 표시하고 재확인 제공. 실제 모델 성공·실패 동작의 운영 검증은 아직 없음 |
| 담당자 대상/회사 선택, 수정, 사유, 승인/반려 | 완료 | 확인 체크·사유·필수값 검사 후 승인, 일괄 승인 제외 |
| 승인 전 변경 항목·대상 요약 | 완료 | 변경 필드 목록/개수, 신규/업데이트 대상 표시 |
| 모든 미해결 충돌의 승인 차단 | 부분 | 필수값·이메일 충돌·대상/회사 버전 검사는 있음. 회사+성명 후보 충돌 등의 명시적 해결 상태 관리 및 승인 직전 전면 재검사는 없음 |
| 표준 회사명·별칭·분류·Contact 수와 영향 확인 | 완료 | 회사 단위 편집 및 사유 기록, 소속 Contact 수 표시. 유사명 자동 병합 없음 |
| 회사의 별도 확인 상태, 분류 충돌 정비 목록 | 부분 | 분류값 ‘확인 필요’로 보류 표현. 별도 확인 상태 및 같은 회사명/상이한 분류 충돌 목록은 없음 |
| 전체 변경 이력: 승인자·시각·전후값·사유·출처 | 부분 | 전후 JSON/사유/행위자/시간, 승인 시 제출 출처 저장. 제출자·부문·대상 ID를 구조화해서 조회/필터하는 화면은 없음 |
| 이메일/회사+성명/명시 대상/복수 후보 비교 | 완료 | 규칙 기반 4종 분류. 단, 미존재 DB ID는 일반 제출 API에서 오류로 거부하므로 ‘확인 필요’ 제출이 생성되지 않는 차이가 있음 |
| 동일 정보 ‘변경 없음’ 종결 | 미구현 | 변경 항목 0개 표시는 가능하나 종결 액션/상태는 없음 |
| 제출 배치/기존 미처리 제출 중복 검사 | 부분 | 제출 시 검사함. 검수 재조회와 승인 트랜잭션에서는 미처리 제출 중복을 다시 검사하지 않음 |
| 회사명 표기·승인 별칭 후보, 기존 회사 분류 적용 | 완료 | 법인 표기/공백 변형은 후보로 취급, 최종 반영은 담당자 확인 |
| 신규 회사명·도메인 기반 AI 분류 추천 | 연결 대기 | Anthropic 호출 코드 존재. 마지막 배포 확인 기준 API 키·모델 환경변수 미설정, 실제 호출 미검증 |
| 개인 이메일 제외·기업 도메인 단독 확정 금지 | 완료 | AI 입력에서 개인 이메일 도메인 제외, AI는 추천만 반환 |
| AI 스키마·후보 ID 검사, 입력 최소화, 쓰기 권한 없음 | 완료 | 허용 분류/후보 ID/근거 검사. 원본 전체·Contact 이름·연락처는 AI에 보내지 않음 |
| AI 규칙 버전·모델·생성시각·추천/결정 보존 | 부분 | 규칙 버전·모델·최신 추천 저장. AI 생성시각과 재검증별 이전 결과 이력 없음. 재검증은 기존 JSON을 덮어씀 |
| 승인 원자성·권한·버전·이메일 유일성·재전송 처리 | 완료 | 승인 트랜잭션·기능 잠금·감사 기록·버전 충돌·중복 승인 방지 구현 |
| 승인 직전 최신 Master 및 배치 중복 전체 재검증 | 부분 | 최종 이메일/필수값/버전은 재검사. 회사+성명 및 미처리 제출 중복을 최신 기준으로 재검사하는 로직은 없음 |
| 최초 이관·원본 18필드·출처·파일 해시·원본 보존 | 완료 | 7,294건 이관 및 원본 행 보존. 기존 회사명 기준 2,826개는 동일 법인 검증 완료 수가 아님 |
| 최초 이관의 회사명/분류 충돌 검출·정비 목록 | 미구현 | 동일 이름/동일 분류 단위로 회사 생성. 다른 분류면 별도 회사가 될 수 있으며 충돌 목록을 생성하지 않음. 제공 파일에서는 이 기준의 충돌 0개 |
| 비검수자/차단 사용자 Master 쓰기 차단 | 완료 | Contact 승인·회사 변경 RPC는 접근/검수 권한 검사. 클라이언트 테이블 직접 쓰기 차단 |
| 제한 운영의 모든 DB 관리 동작 접근 차단 | 부분 | 검수자 지정 RPC에 마케팅 접근 허용목록 검사가 누락됨. 아래 P1 참고 |
| 모바일·빈 화면·로딩·API 오류·키보드 수용 테스트 | 부분 | 기존 렌더/일부 UI 검사 및 탭 전환 회귀 테스트 있음. 전체 키보드 접근성과 모든 실패 경로에 대한 인수 검증 완료 근거는 없음 |
| Stibee·Eco 동기화·월간 보고 | 후속 범위 | 미구현이지만 1차 제외 항목이므로 1차 누락으로 계산하지 않음 |

## 우선 보완 사항

### P1 — 권한과 승인 정합성

1. **검수자 지정 RPC 권한 예외**: `marketing_set_reviewer`는 관리자 역할만 검사하며 `has_page_access('marketing')`를 검사하지 않는다. 앱 API는 차단하지만, 허용목록 밖의 관리자도 DB RPC 직접 호출 시 검수자 설정과 관련 감사 기록을 변경할 수 있는 구조다. 운영 함수 정의에서도 확인했다. 이것이 해당 관리자에게 Master 조회/승인 권한을 주는 것은 아니지만, 앞서 안내한 ‘모든 DB 접근 차단’은 이 관리 동작까지 포함하면 부정확했다. 함수 내부 접근 검사와 직접 RPC 회귀 테스트가 필요하다.
2. **승인 직전 중복 재검사 부족**: 제출 후 새 Contact가 생기거나 검수자가 최종 이름/회사/대상을 변경한 경우, 이메일 유일성 외 회사+성명 중복·대기 제출 충돌을 승인 트랜잭션에서 다시 확인하지 않는다. 명시적 충돌 해결 절차와 서버 재검증이 필요하다.
3. **원본 DB ID와 이메일 충돌 해소 절차**: 근거 표시와 대상 수동 선택은 있으나 모든 미해결 충돌을 승인 불가 상태로 관리하지 않는다. 설계대로 재검증/해결 여부를 기록하도록 보강해야 한다.

### P2 — 1차 요구 충족 및 업무 사용성

- AI 키·모델 연결 및 실제 신규 회사/유사 법인 사례 검증. 현재 코드의 회사 후보 검색은 승인 별칭과 법인 표기/공백 비교 중심이며 폭넓은 오탈자·약칭 탐색은 보장하지 않는다.
- Master 관리부서 필터, Contact별 변경 이력, 제출 상세의 반려 사유 표시.
- Excel 부분 성공 정책 구현 또는 ‘오류도 검수 요청으로 수집하는 일괄 처리’로 명세 변경 합의. 미존재 DB ID도 행별 결과에 표현.
- 회사별 분류 충돌 목록과 확인 상태, ‘변경 없음’ 종결.
- 검증 결과의 생성시각·재검증 이력 보존, 승인 결과와 당시 추천을 연결하는 감사 추적.

### P3 — 전체 수용 검증

키보드 탐색, API 실패/시간 초과, AI 실응답 오류, 부분 실패/재제출, 승인 직전 새 중복 발생을 포함해 설계의 수용 테스트를 다시 실행한다. 기존 테스트 통과는 위 누락 기능의 완료를 의미하지 않는다.

## 설계와 다른 데이터 구조

- `marketing_organization_aliases` 별도 테이블 대신 `marketing_organizations.aliases` 배열 사용. 변경 전후 회사 감사 기록은 있으나 별칭별 독립 승인 레코드는 없다.
- `marketing_validations` 별도 테이블 대신 `marketing_submissions.validation` JSON 사용. 제출 버전은 증가하지만 이전 검증 결과는 별도 보존하지 않는다.
- 조직 분류 확인 상태는 별도 컬럼 대신 분류 ‘확인 필요’로 표현한다.
- Contact 기본 필드는 `data` JSON, 회사 관계와 DB ID/버전은 별도 컬럼으로 관리한다.

구조 변경 자체를 모두 결함으로 보지는 않는다. 다만 검증 이력·확인 상태처럼 설계에서 약속한 기능이 줄어든 부분은 별도로 보완해야 한다.
