# 마케팅 검수자 관리 및 검수 처리

2026-09-15 최신 변경. 처음 두 사람만 접근하도록 제한한 운영에서, **강승억·김하연이 추가 검수자를 지정하는 방식**으로 변경했다.

## 역할과 검수자 추가

| 구분 | 권한 |
|---|---|
| 고정 검수 관리자: 강승억·김하연 | 마케팅 접근·검수 및 다른 검수자 추가·해제 |
| 지정된 검수자 | 마케팅 접근·모든 부문 Contact 검수·승인·반려, 회사 기준·관리 규칙 수정, 규칙 검증·이메일 검사 |
| 미지정 사용자 | 마케팅 접근 및 자기 등록 불가 |

- `/marketing` 상단 **검수자 관리 → 검수자 추가**에서 이름·이메일 2자 이상을 검색한다. 서비스 가입과 사용자 승인이 완료된 계정만 대상으로 한다. 이미 지정된 사용자와 고정 관리자는 추가 검색에서 제외한다. 검색 결과는 20건씩 조회한다.
- 대상을 선택하면 마케팅 접근·검수 권한이 부여된다는 안내를 확인한 뒤 **지정 적용**한다. 새 검수자에게 검수자 관리 권한은 부여하지 않는다.
- 김하연은 서비스 전체 관리자 역할이 아니어도 검수자를 추가·해제할 수 있다. 서비스 전체 관리자라도 지정받지 않은 계정은 마케팅 접근/자기 등록이 불가능하다. 지정받은 일반 관리자의 검수자 관리 권한도 자동으로 생기지 않는다.
- 추가된 검수자는 **검수자 정보**에서 목록·실제 권한·부여 근거·지정자·시각·감사 이력을 읽을 수 있다. 사용자를 검색하거나 자신/다른 사람의 권한을 바꾸는 API·DB RPC는 거부한다.
- 검수자 해제 시 추가된 계정의 **마케팅 접근과 검수 권한이 함께 해제**된다. 서버 요청에서 현재 권한을 다시 검사하고 메뉴는 새로고침하면 갱신된다. 기존 검수·지정 이력은 보존한다.
- 고정 관리자 두 계정은 이 관리 화면으로 추가·해제할 수 없다. 사용자 이름 변경이나 동명이인으로 권한이 생기지 않도록 고정 계정 ID와 승인된 역할로 판단한다.
- 검수자 지정은 개별 Contact 담당자 배정·초대 이메일·알림 발송 기능이 아니다. 최초 Master Excel 이관은 기존 서비스 관리자 조건을 유지한다.

## 저장·감사·동시 변경

`marketing_reviewers.user_id`가 추가 검수자의 접근·검수 권한 근거다. 고정 관리자는 별도 내부 판단 함수로 구분하며, 기존 두 계정의 명시적 지정 행과 과거 이력도 보존한다.

지정·해제는 `marketing_review_events`에 처리자, 시각, 대상 계정 ID/당시 이름/이메일, 변경 전후 권한을 기록한다. 현재 지정자·시각은 최근 지정 감사 기록에서 조회하며 기록이 없으면 미상으로 표시한다. 예전 ID만 있는 기록은 현재 프로필을 연결한다. 실제 변경 없이 같은 상태를 요청하면 이력을 중복 생성하지 않는다.

계정별 잠금과 현재 버전 비교를 적용한다. 오래된 화면의 변경은 409로 거부하고 최신 목록을 다시 읽는다. 권한 변경과 감사 기록은 한 DB 트랜잭션이며 기록 실패 시 권한 변경도 롤백한다. 테이블 및 내부 함수에 대한 일반 클라이언트의 직접 쓰기를 허용하지 않는다.

## 반려 방법

검수 상세 상단 **반려 사유 입력 → 사유 2자 이상 입력 → 사유를 저장하고 반려**로 처리한다. 아래쪽 공통 검수 사유를 입력한 뒤 **반려**를 눌러도 된다. 반려는 최종값 재검증이나 승인용 체크가 필요하지 않다. Master는 변경되지 않으며 사유는 변경 이력과 제출자 화면에 남는다. 제출자는 내용을 보완해 다시 제출할 수 있다.

같은 Master를 대상으로 불완전한 요청과 이를 보완한 후속 요청이 함께 들어왔다면, 실제로 대체 관계인지 검토한 뒤 이전 요청을 반려하고 후속 요청을 다시 검증한다. 다른 대기 요청을 처리하면 검증 토큰이 달라지므로 승인할 요청에서 최종값 재검증을 다시 해야 한다. 시스템이 요청을 임의로 반려하지 않는다.

## 최종값 검증의 차단 오류와 확인 항목

- **승인 차단 오류**: 잘못된 이메일·다른 Contact가 사용 중인 이메일·필수정보 누락 등 현재 규칙의 오류. 최종값을 수정하고 재검증해야 하며 근거나 체크만으로 통과할 수 없다.
- **담당자 확인 항목**: 회사명 차이·성명/회사 변경·중복 대기 요청·수동 관리 기준 등. 검증에서 제시한 항목을 실제로 확인하고 ‘확인 항목·충돌 해결 근거’에 자료와 판단을 기록한다. 모든 항목을 확인한 경우에만 관리 기준 확인 체크를 한다. 불확실한 분류는 확인 필요로 유지한 이유를 기록할 수 있다.
- Stibee 미연계는 발송 유효성을 확인했다는 의미가 아니다. 수신거부·반송 정제 자료가 없는 상태를 확인 완료로 체크하지 않는다. 확인하지 못한 항목은 검수 대기로 유지하거나 반려한다.

승인 활성화 조건: [등록된 회사·기관 선택](marketing-registered-organizations.md), 최신 Master 비교 완료, 최종값 재검증 완료, 차단 오류 없음, 확인 항목이 있을 때 해결 근거 2자 이상과 확인 체크, 검수 사유 2자 이상, 최종 반영값 확인 체크. 값을 바꾸면 다시 검증한다. 확인 근거 내용의 사실 여부는 담당자가 판단하며 AI 미연결은 승인 조건이 아니다.

화면 상단에서 **승인 조건·처리 버튼으로 이동**할 수 있고 하단 **승인까지 남은 작업**에 미충족 조건이 표시된다. 확인 항목마다 동일 인물·법인, 대기 중복, 표준명, 분류, 정제 자료의 확인 방법을 안내한다. 기존 검증 기준과 승인 차단 조건을 약화하지 않았다.

## 적용 및 검증

- 기존 SQL 이후 `docs/sql/2026-09-15-marketing-reviewer-delegation.sql` 적용. 마케팅 접근 분기만 변경하며 다른 페이지의 권한 정책은 그대로 유지한다. 적용 시 새로운 검수자를 임의 등록하거나 기존 제출을 처리하지 않는다.
- `GET /api/marketing/reviewers?page=1`: 현재 목록과 감사 이력. `?q=이름&page=1`: 고정 관리자 전용 후보 검색. `POST`: `{userId, enabled, version}`으로 지정·해제.
- DB: `marketing_can_manage_reviewers`, `marketing_reviewer_candidates`, `marketing_update_reviewer`. 기존 `marketing_set_reviewer` RPC도 고정 관리자 조건을 동일하게 적용한다.
- 메뉴·페이지·API·RLS는 기존 `has_page_access('marketing')`를 통해 현재 DB 멤버십을 조회한다.
- Native SQL: `scripts/check-marketing-reviewer-delegation.sql` (격리 로컬 DB, 전체 롤백). 김하연의 관리 권한, 일반/전체 관리자의 자기 등록 차단, 신규 검수자 권한 및 다른 사용자 추가 금지, 해제 후 접근 차단, 고정 관리자 보호, 후보 검색 제한, 버전 충돌, 감사 원자성을 검사한다.
- 관련 UI/API·메뉴/미들웨어 테스트 51개 통과. 권한 후보 검색·추가, 일반 검수자의 관리 금지, 반려를 검증 없이 처리하는 흐름, 확인 항목 해결 및 승인 조건, 기존 검수·접근 회귀를 검증했다. TypeScript·ESLint·production build 통과.
