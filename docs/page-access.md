# 사용자별 페이지 접근 권한

관리 화면: `/admin/page-permissions`. 사용자 검색 → 선택 → 페이지/그룹 허용·차단 → 변경사항 저장. 기본 권한으로 되돌리기는 편집값을 초기화하며 저장해야 반영된다. 변경 이력은 기존 Audit 로그에 남긴다.

## 메뉴와 기본값

- 일상·팀 활동: 뭐 먹지, 사다리, 커피 타임, 설문
- AI·성과: Claude Code, Claude 채팅, 성과
- 업무·소식: RFP 분석, 인사·부고
- 가이드는 기존 메뉴 숨김을 유지하며 직접 접근 권한은 별도로 관리한다.
- 관리자: 항상 전체 허용. 게스트: 일상·팀 활동만 역할상 허용. 사용자: 모든 사용자 페이지 허용. 개별 설정은 역할을 승격시키지 않는다.
- 설정·프로필·매뉴얼은 공통 메뉴다. 공개 설문과 외부 RFP 공유의 익명 공개 정책은 유지한다. 기존 메일 예약은 페이지 접근 권한과 별도로 계속 실행된다.

## 구현과 보안

`lib/page-access.ts`가 그룹, 페이지 식별자, 최소 역할, 페이지/API 경로를 정의한다. 메뉴·홈 카드·관리 화면·프록시에서 공용으로 사용한다. 경로는 슬래시 경계로 비교한다. 프록시는 요청마다 프로필과 접근 설정을 조회하며 확인 실패 시 보호 페이지/API를 허용하지 않는다. 이미 열린 메뉴는 포커스 복귀 및 30초 갱신으로 변경을 반영한다. 로그아웃·계정 전환 시 이전 역할 캐시를 즉시 지운다.

`user_page_access`는 사용자당 한 행의 JSON 권한과 버전을 저장한다. 값이 없는 페이지는 역할 기본값을 따른다. RLS로 본인 또는 관리자만 조회 가능하며, authenticated의 직접 쓰기는 금지한다. 관리자 전용 `set_user_page_access` RPC가 유효 키/boolean 값, 관리자 보호, 낙관적 동시성 검사를 수행한다. 동일 사용자의 프로필 행을 잠가 동시 역할 변경과 권한 변경을 직렬화한다. stale version은 409로 반환한다.

직접 DB로 읽는 설문/팀/사다리/인사·부고 테이블에는 기존 소유권 정책에 추가되는 restrictive RLS를 적용한다. 인사·부고의 SECURITY DEFINER RPC와 수집 Edge Function도 페이지 제한을 검사한다. 서비스 역할 및 전용 cron은 기존 작업 권한을 유지한다.

새 사용자 페이지 추가 시 공용 카탈로그와 SQL 허용 키·역할 기준, 관련 API 경로를 함께 추가한다. 여러 페이지가 공유하는 API는 실제 소비 페이지 중 하나라도 허용된 경우에만 열어준다.

## 배포 및 검증

1. `supabase db query --linked --file docs/sql/2026-09-11-page-access.sql` 적용. 설정 행을 생성하거나 기존 사용자를 차단하지 않는다.
2. `supabase functions deploy yonhap-notices --project-ref avooqcxehfeurjhqqgui --use-api`
3. frontend에서 `vercel --prod --yes`.
4. `scripts/check-page-access.sql`은 테스트 제한과 역할 변경을 모두 롤백한다. 일반 사용자 변경 금지, 관리자 보호, 낙관적 버전 검사, DB/RPC 직접 접근 차단을 검증한다.

롤백 시에는 이전 frontend/Edge를 복원하고 추가한 `page_access_limit` 정책을 검토해 제거한다. 권한 테이블과 설정 기록은 보존한다.
