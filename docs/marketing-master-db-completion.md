# 마케팅 Master DB — AI 제외 1차 보완 구현

> 후속 보완: 오류 Contact의 확인 필요 수집과 김하연 검수자 지정을 추가했다. 최신 접수 정책·권한 검증은 [최종 접수·검수자 보완](marketing-master-db-intake-reviewer.md)을 참조한다.

2026-09-14. 이전 [설계 대비 점검](marketing-master-db-implementation-audit.md)에서 확인한 비-AI 보완 항목을 구현했다. AI 연결 및 실제 모델 응답 검증은 사용자 요청으로 마지막 단계에 남겨두었다. Stibee·Eco 외부 동기화·월간 리포트는 기존 합의대로 후속 범위다.

## 이번 구현

| 항목 | 구현 결과 |
|---|---|
| 검수자 지정 DB 권한 예외 | DB 함수 자체에서 마케팅 접근 허용목록과 관리자 역할을 함께 검사. 허용목록 밖 관리자도 직접 RPC 실행 불가. 검수자 목록 RLS도 같은 접근 제한 적용 |
| 승인 직전 최신 중복 검사 | 최종 회사·성명·이메일, 원래 지정 DB ID/이메일, 다른 대기/검증 중 제출을 비교. 승인 트랜잭션에서 다시 검사 |
| 명시적 충돌 해결 | ‘최종값 재검증’에서 충돌을 표시하고 해결 근거·확인 체크 요구. 최종값·대상·후보 버전이 바뀌면 이전 검증 토큰은 승인에 사용할 수 없음 |
| 최종 이메일 충돌 | 다른 Contact의 이메일이면 수정/대상 재선택 전 승인 차단. 단순 해결 체크로 통과할 수 없음 |
| 변경 없음 종결 | 최종 필드와 기존 회사/Contact가 모두 같을 때만 허용. 제출 상태와 감사 기록만 저장하고 Master와 Contact 버전은 변경하지 않음 |
| 검증 중 상태 | 제출을 검증 중으로 먼저 기록하고 검사 완료 후 검수 대기로 전환. 중단된 건은 ‘검증 중’ 목록에서 검수 담당자가 다시 검증 가능 |
| Master 관리부서 필터 | 기존 내부 관리부서 기준 서버 검색 추가. 사내 제출부문 필터와 구분 |
| 정비 필요 표시 | 회사·성명 누락/분류 미확인 Contact에 ‘기존 데이터 정비 필요’ 표시와 기존 정비 필터 제공 |
| Contact별 변경 이력 | 상세에서 Contact 변경과 현재 소속 회사의 기준 변경 이력 확인 |
| 반려 사유 | 제출 상세에 검수자·반려 사유·시각을 표시하고 수정 재제출 제공 |
| 이력 검색 | 전체 변경 이력에서 제출자·승인자·DB ID·사유 검색, 제출부문 필터. 전후값·원본출처·승인 당시 검증을 펼쳐 확인 |
| Excel 부분 성공 | 행별 검증·저장. 성공 행은 유지하고 오류 행의 행번호/원인 제공. 화면에서 오류 행을 수정해 미제출 행만 재시도 |
| Excel 입력 오류 | 필수값 누락/형식 오류는 확인 필요로 접수. 없는 DB ID나 읽을 수 없는 셀 등은 해당 행의 접수 실패로 표시. 업데이트 빈칸은 기존값 유지. 수식은 실행하지 않고 문제 셀을 수정하도록 안내 |
| 원본과 재시도 | 원래 파일·해시·시트·행·원문은 보존. 수정 입력은 별도로 제출하며 요청 키로 중복 저장 방지. 연결 장애 후 같은 입력 재시도도 중복 생성하지 않음 |
| 회사 확인 상태 | 분류와 별도로 확인 필요/확인 완료 관리. ‘확인 필요’ 분류는 확인 완료 처리 불가. 담당자 사유와 회사 전후 스냅샷 기록 |
| 회사 분류 충돌 정비 | 동일 표기와 다른 분류의 회사 그룹, 미확인 그룹 수 표시. 최초 이관 미리보기에도 동일 이름·다른 분류의 행 목록 표시. 자동 병합 없음 |
| 검증 이력 | `marketing_validations`에 생성시각·제출 버전·규칙 버전·모델/추천 결과 누적 저장. 재검증이 이전 결과를 지우지 않음 |
| 감사 연결 | 승인/반려/종결에 Contact·회사·제출자·부문·출처·당시 검증을 연결. 승인 충돌 목록과 해결 근거도 보존 |
| 키보드/모바일 | 탭 방향키·Home/End, 폼·체크박스·승인 버튼 키보드 조작. 모바일 비교 화면은 표 내부 스크롤 사용 |

## 현재 운영 범위

- 마케팅 접근 계정은 **강승억·김하연** 두 계정으로 유지한다. 접근 권한과 검수 권한은 별개이며 후속 사용자 요청에 따라 김하연을 명시적으로 검수자로 지정했다.
- 단건과 Excel 신규 제출은 회사명·성명·이메일이 누락돼도 확인 필요로 접수되며, Master 승인 전에는 보완해야 한다. 기존 이관 데이터의 누락은 보존한다.
- Excel의 없는 DB ID는 ‘확인 필요’ 제출을 새로 만들기보다 **해당 행 입력 오류**로 반환한다. 검수 단계의 네 분류는 유효한 제출에 대한 기존 Master 비교 결과다.
- 별도 법인 여부는 담당자가 확인한다. 회사 확인 상태 변경과 충돌 그룹의 검토가 실제로 끝났다고 자동 간주하지 않는다.
- 검증 이력을 추가하기 전에 존재했던 제출은 당시 최신 결과만 보존한다. 이관한 기록에는 원래 생성시각이 아닌 보존 시각임을 명시한다. 과거에 덮어쓴 추천을 복원하지는 않는다.

## 사용 순서

1. Contact 등록 또는 Excel 제출. Excel은 미리보기 → 제출 → 오류 행 수정 → 남은 행 재제출 → 완료 순서다.
2. 검수 대기에서 대상 Contact·회사와 최종값을 정한다.
3. **최종값 재검증**을 실행한다. 필수값·이메일 충돌은 수정하고, 동명이인/별도 법인/다른 대기 제출은 해결 근거를 작성한다.
4. 검수 사유와 최종 확인 후 승인, 반려 또는 변경 없음 종결을 선택한다. 기준이 바뀌었다는 오류가 나오면 새로고침 후 다시 검증한다.
5. Master 상세 및 변경 이력에서 결과와 출처를 확인한다. 회사·기관 탭에서 분류 충돌 그룹과 확인 상태를 관리한다.

## 검증 기록

- TypeScript 및 변경 범위 ESLint 검사 통과.
- 원본 Excel 대조를 포함한 규칙·권한·화면·행별 API 테스트 **57개** 통과.
- 별도 로컬 PostgreSQL에서 최초 SQL 검증과 보완 수용 검증 실행. 검증 중→대기, 추천 이력 누적, 직접 RPC 권한 거부, 충돌 차단/해결, 검수 중 새 중복 발생 시 이전 확인 거부, 변경 없음 종결, 회사 확인 상태/분류 충돌 목록, 원본·제출자·검증 감사 연결 확인. 테스트 데이터는 롤백.
- 실제 React 화면과 가상 API를 사용한 Chrome 검증: 최종값 재검증·충돌 근거·승인 갱신·키보드 이동, 390px 모바일 가로 넘침 없음.
- 운영 검증에서는 실제 연락처를 테스트로 수정·승인하지 않는다. 배포 후 조회·필터·이력·차단 동작과 이관 건수를 확인한다.

SQL 보완 수용 테스트: `scripts/check-marketing-completion.sql` — **별도 로컬 DB 전용**.

## 마지막 단계: AI

현재 AI 호출은 `MARKETING_AI_ENABLED=true`일 때만 가능하게 해 두었으며 기본값은 비활성이다. 실제 연결 시 `ANTHROPIC_API_KEY`, `MARKETING_AI_MODEL`을 설정하고 모델 성공/실패/시간 초과/잘못된 응답 및 실제 회사 후보 추천 품질을 별도로 검증한다. 이번 완료 범위에 AI 실연결 검증은 포함하지 않는다.
